# 日日说 · M0 技术验证报告

> 2026-10-11 · 验证环境：2 核 x86 服务器（3.5GB 内存）+ headless Chrome 147 · 脚本见 `spikes/m0/`

## 一句话结论

**离线发音评分这条路走得通，可以进入 M1。** 一个 122MB 的模型就能在本机给中国学习者逐音素打分，和人工评分的吻合度接近学术界同数据集的水平；同一套评分在浏览器里离线可用，经过微信语音编码也几乎不掉精度。

**两个短板要在 M1 重点解决**：整句分偏高（“加尾音”这类典型错误扣分不够）；浏览器端推理速度在低端手机上可能不够快。

## 2. 发音评分

### 2.1 数据与方法
- **评测集**：speechocean762（CC BY 4.0）。中国母语者朗读英语，每个音素有人工打分（0 = 错/漏读，1 = 重口音，2 = 正确）。测试集 2500 句 / 47369 个音素，训练集 2500 句。
- **模型**：charsiu `en_w2v2_ctc_libris_and_cv`，wav2vec2-base 结构的音素识别模型，用 LibriSpeech 和 Common Voice 训练，直接输出 CMU 音标（和 CMUdict 同一套）。导出为 ONNX 后做 int8 动态量化。
- **评分（GOP）**：免对齐 CTC-GOP。对句子里每个音素，比较“读对了”与“这个位置被读成其他 38 个音素或漏读”的概率，得到它“读对”的份额。
- **校准**：用训练集拟合一个小的梯度提升树（237KB JSON），把 GOP 分数映射到人工的 0～2 分刻度。

### 2.2 结果（测试集，全部 2500 句）

| 方法 | 音素级相关 | 成人子集 | 检错 AUC |
|---|---|---|---|
| 未校准 GOP | 0.463 | 0.482 | 0.868 |
| 线性校准 | 0.535 | 0.542 | 0.866 |
| **树模型校准（完整特征）** | **0.603** | **0.629** | **0.891** |
| 树模型校准（仅免对齐特征，前端在用） | 0.591 | — | 0.889 |

- 对照：GOPT 论文（Gong et al., 2022）在同一测试集上报告的音素级相关约 0.61，用的是服务端训练的 Transformer 打分器。**我们用一个能放进手机的模型做到了接近的水平。**
- int8 vs fp32（同 500 句）：音素相关 0.343 对 0.348，逐帧识别 98.4% 一致，速度快一倍。**结论：用 int8。**
- 词级相关 0.45，句子级（仅音素分均值）0.57。

### 2.3 红黄绿怎么划（宁可漏报，不冤枉）

| 校准分阈值 | 标出比例 | 标出的音素里确实需要纠正的比例 | 需要纠正的音素被标出的比例 |
|---|---|---|---|
| < 0.8（**标红**） | 1.6% | **76%** | 18% |
| < 1.4（**标黄**） | 5.8% | 53% | 45% |

意思是：标红的基本靠得住；但轻微口音大约有一半不会被标出来。这符合“鼓励优先”的产品原则，但也说明细微口音的识别要靠后续微调模型来提升。

### 2.4 发现的短板：“加尾音”和整句分虚高
用一句人工只给 4/10 的录音（"Just set hook and put the pressure"）检查：
- 模型其实**听出了加尾音**：set 读成 "seita"，put 读成 "porta"。但逐音素评分只评“该有的音读得对不对”，**多读出来的音不扣分**。
- 校准回归有“向平均靠拢”的倾向：数据里 93% 的音素人工分 ≥ 1.5（基本正确），模型学到“多数时候猜正确就对”，明显错误也只被判成“略差”。

已验证的补救方法：把识别出的音素序列和标准读音对齐，统计多读、漏读、替换和语速，作为句子级特征：

| 句子级特征 | 线性模型 | 树模型 | 树模型·成人 |
|---|---|---|---|
| 仅音素分均值 | 0.568 | 0.598 | 0.685 |
| + 多读 / 漏读 / 替换 | 0.650 | 0.620 | 0.705 |
| + 语速 | **0.667** | 0.653 | **0.757** |

这句在演示页里按音素分均值得 85 分（相当于 8.5/10），用加了对齐特征的句子级模型后是 7.3/10。方向对了，但仍然偏高。**M1 需要继续处理。**

### 2.5 发音评分在产品里的定位
- 适合：跟读评分、找出明显读错的音、追踪“最常错的 10 个音素”、声音日记对比。
- 暂不适合：精确到“轻微口音”的逐音诊断、当作雅思发音分的直接预测。界面上要明确写“练习参考”。

## 3. 浏览器端

### 3.1 推理一致性与速度
| 配置 | 3 秒音频耗时 | 实时率 | 备注 |
|---|---|---|---|
| Python 原生（onnxruntime，单线程，int8） | ~0.4 秒 | 0.13 | 代表 App 原生推理的上限 |
| **浏览器 WASM 单线程 int8（选用）** | **~1.7 秒** | **0.56** | 断网可用；模型建会话 ~1.6 秒（只在首次） |
| 浏览器 WASM 单线程 fp32 | ~2.2 秒 | 0.74 | 比 int8 慢，且模型大 3 倍 |
| 浏览器 WASM 双线程 int8（COOP/COEP） | ~1.4 秒 | 0.48 | 提升有限；**断网时卡死**（见下） |

- 服务器 CPU 上浏览器比原生慢约 4 倍。手机 CPU 一般比这台服务器的单核慢 2～4 倍，所以**手机浏览器上 3 秒的句子估计要 3～7 秒**，体验不达标。必须真机实测，并准备好提速方案（WebGPU、App 原生推理、更小的模型）。
- **多线程 + 断网的坑**：开启 COOP/COEP 后，onnxruntime 的线程 worker 和 SQLite 的 OPFS 代理（worker 里再起的 worker）在断网时会二次加载失败，onnxruntime 一直等线程就绪，整页卡住。预缓存清单里已经有这些文件，诊断确认页面层面的请求确实走了 Service Worker，问题在 worker 内部的加载。**处理：网页版默认单线程**（已验证断网可用），多线程留到 M1 再定位。

- 浏览器输出和 Python 的逐帧识别 98～100% 一致（int8 在 WASM 里的量化计算路径不同，有少量数值差，不影响评分）。
- **GOP 评分**：JS 实现（`web/gop.mjs`，前向/后向复用，单句 O(N·K·T)）与 Python 在 200 句、3634 个音素上最大误差 0.00016，平均每句 39ms。
- **校准模型**：JS 推理与 sklearn 最大误差 7e-6，每个音素约 70 微秒。

### 3.2 离线与持久化
| 步骤 | Service Worker 接管 | 数据库行数 | 模型载入 |
|---|---|---|---|
| 首次在线打开 | 否 | 0 → 1 万 | 网络下载 ~1.2 秒 |
| 刷新 | 是 | 1 万 → 2 万 | 缓存 ~0.24 秒 |
| **服务器真断开后刷新** | 是 | 2 万 → 3 万 | 缓存 ~0.27 秒 |

- 数据库：官方 SQLite WASM + `opfs-sahpool` VFS。不需要 COOP/COEP，Safari 也支持；10000 条写入约 0.2 秒。
- Service Worker 采用**安装时预缓存完整清单**（含懒加载的 worker 脚本和 wasm），不能只靠“访问过才缓存”。
- 坑：Puppeteer 的 `setOfflineMode` 不影响 Service Worker 的判定，测离线必须真停服务器。

### 3.3 演示页
`spikes/m0/web/demo.html`：选句子或自定义 → 录音 → 逐音素红黄绿 + 发音提示 + 整句分，浅色/深色跟随系统。headless Chrome 用模拟麦克风验证了全链路（录音编码为 Opus → 解码 → 16k 重采样 → 推理 → 打分）。

## 4. 微信语音（SILK）
- 用 silk-wasm（SILK v3，和微信同一编码）把测试集全部 2500 句编码再解码（24kHz，平均 31kbps），重新评分：音素相关 0.603 → 0.598，检错 AUC 0.891 → 0.890。**基本无损。**
- 未验证：微信实际采用的码率可能更低；ClawBot 是否把原始语音交给 agent（见方案第 14.2 节）。要用真实微信语音实测。

## 5. 对方案的修正
1. **模型**：确定使用 charsiu wav2vec2-base 音素 CTC（int8，122MB），不需要 300M 参数的大模型。
2. **评分 = 三层**：
   - 逐音素 GOP；
   - 树模型校准；
   - 句子级加入“多读/漏读/语速”。
   前两层在前端已实现并对拍通过，第三层 M1 移植到 JS。
3. **分档阈值**：红 < 0.8，黄 < 1.4。界面文案用“建议注意”，不用“错误”。
4. **App 端优先原生推理**：Tauri 走 Rust 的 onnxruntime / sherpa-onnx，速度约为 WASM 的 3 倍以上；网页版保留 WASM，并提示“首次需下载 122MB 模型”。
5. **微信纠音可行**：前提是 agent 能把音频交给工具（方案第 14.2 节的自检）。

## 6. M1 待办（按优先级）
1. **真机测速**：在你的安卓手机和 iPhone 上打开演示页，看真实速度。需要先把演示页部署到可以 HTTPS 访问的地址，因为浏览器要求 HTTPS 才能用麦克风。
2. **加尾音 / 漏尾音检测**进入逐音素层：把多读的元音挂到前一个词上，在界面上直接提示“set 后面多了个 a”。
3. **模型微调**：用 speechocean762 训练集加 L2-ARCTIC（需申请）在中国口音上微调，目标音素相关 ≥ 0.65、标黄召回 ≥ 0.6。
4. **提速**：WebGPU（支持的设备）+ 多线程；评估更小的模型（蒸馏到 6 层）。
5. **Tauri 安卓**：CI 构建一个最小 APK，跑原生推理测速。
6. 自由口语的 ASR（sherpa-onnx）和离线 TTS（Piper / Kokoro）技术验证：这两项风险低，放到 M1 前期顺带验证。
